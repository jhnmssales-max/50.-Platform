# Referral platform API

Referral platform API, per the [backend spec](../supabase/README.md): dealer-facing endpoints (creating a referral link and emailing it, listing/searching referrals, marking one paid) and public endpoints (resolving a link, generating a share link, submitting a referral). No gift card integration yet.

## Endpoints

### `POST /api/customers`

A dealer enters a customer's name/contact; the customer and their invite (referral) link are created atomically in one transaction, then the invite is emailed to them through Postmark.

```
POST /api/customers
Authorization: Bearer <supabase access token>
Content-Type: application/json

{ "name": "Sarah Johnson", "email": "sarah@email.com", "phone": "7175550134" }
```

```json
{
  "customer": { "id": "...", "name": "Sarah Johnson", "email": "sarah@email.com", "phone": "7175550134", "created_at": "..." },
  "invite_link": { "code": "sarahjohnson-8m27uh", "url": "https://acme.50platform.com/fifty-template-customer.html?code=sarahjohnson-8m27uh", "status": "active", "created_at": "..." },
  "email": { "sent": true }
}
```

Sending is a best-effort side effect, attempted only *after* the customer and link are safely committed — if Postmark fails (bad recipient, bad token, network error), the response is still `201` with the customer and link both real, just `"email": { "sent": false, "error": "<Postmark's message>" }`. The link is always returned either way, so the dealer always has something to hand over manually if the email didn't go out.

### `GET /api/me`

Who the caller is: `{ "name", "email", "role", "tenant_name" }`, read from `users`/`tenants` via the same `getCallerContext` every other route uses. `403` if the token belongs to no staff account. This is what the dealer page calls right after sign-in to show "Signed in as ... · dealer" and to decide client-side whether to let this session interact with the "mark as paid" toggle — display only, never a trust boundary; `PATCH /api/referrals/:id/status` still enforces admin-only server-side regardless of what this returns.

### `GET /api/referrals`

The dealer's searchable pipeline — one row per friend who has submitted the lead form against one of the dealer's customers' share links. This is the "Referrals in progress" list from the dealer page prototype, now backed by a real query instead of browser storage.

**Scoped by role, not just by tenant**: a dealer sees only referrals that trace back to a customer *they* invited; an admin sees every referral in the tenant. This isn't an `if (role === 'admin')` in this file — it's enforced by the RLS policy in `supabase/migrations/20260906000000_referrals_dealer_scope.sql`, the same "the database decides, not application code" property as everything else here. A dealer's `query`/`status` filters run against that already-narrowed set, so there's no way to search your way into seeing a coworker's referrals.

Status lives **per referral, not per customer**: a single customer can hold several share links and generate several referrals, and each gets paid out independently — Sarah's referral of Mike can be `paid` while her referral of Priya is still `pending`, on the same customer. "Paid" is `true` once either signal says so: `referrals.status = 'rewarded'` (set by `PATCH /api/referrals/:id/status` below, whether that's an admin marking it by hand or the reward attempt it triggers) or a `gift_card_transactions` row shows `issued` directly. Never stored redundantly as its own column; computed live from whichever signals actually exist. The raw `referrals.status` lifecycle (`new` → `contacted` → `ordered` → `rewarded`, or `declined`) is included alongside the collapsed `pending`/`paid` view for anything that needs more detail.

Query params (all optional): `query` (matches the friend's name/email/phone, or the referrer's name), `status` (`pending` or `paid`), `limit` (default 20, max 100), `offset` (default 0).

```json
{
  "referrals": [
    { "id": "...", "name": "Mike Torres", "email": "...", "phone": null, "message": null,
      "submitted_at": "...", "referral_status": "rewarded", "status": "paid",
      "referrer": { "id": "...", "name": "Sarah Johnson" } },
    { "id": "...", "name": "Priya Patel", "email": "...", "phone": null, "message": null,
      "submitted_at": "...", "referral_status": "new", "status": "pending",
      "referrer": { "id": "...", "name": "Sarah Johnson" } }
  ],
  "pagination": { "limit": 20, "offset": 0, "total": 2 },
  "counts": { "pending": 1, "paid": 1 }
}
```

### `PATCH /api/referrals/:id/status`

Admin-only. Backs the dealer page's "mark as paid" toggle. Body: `{ "status": "contacted" | "ordered" | "rewarded" | "declined" }` — a manual override for statuses that don't yet flow in automatically; setting `rewarded` is exactly what the (not-yet-built) order-system webhook will eventually do on its own once an order comes in, so today a human triggers the same transition a webhook will later.

**Setting `rewarded` now also attempts a real reward** — see "How a reward actually gets issued" below — funded by *this tenant's own* connected Tremendous account, never a shared one. A tenant with nothing connected behaves exactly as before: the status flips, no reward is attempted, `reward` is simply absent from the response.

What this endpoint guarantees regardless: it's server-authoritative (the client sends only a target status, nothing about amounts or "did it work"), and idempotent under real concurrency, not just sequential double-clicks — a guarded `UPDATE ... WHERE status IS DISTINCT FROM $1` means the status transition, and the single `audit_log` row for it, happens exactly once no matter how many identical requests land at once. The reward attempt has the same guarantee, separately (see below): at most one Tremendous order is ever created per referral, no matter how many times or how simultaneously this is called.

```
PATCH /api/referrals/40000000-0000-0000-0000-000000000001/status
Authorization: Bearer <admin's access token>
Content-Type: application/json

{ "status": "rewarded" }
```

```json
{ "id": "40000000-0000-0000-0000-000000000001", "status": "rewarded", "reward": { "issued": true } }
```

`reward.issued: false` carries an `error` message (Tremendous's own, when they rejected the order — e.g. an underfunded funding source) rather than a generic failure — the dealer page surfaces this directly so an admin knows to send that reward by hand, since a failed attempt is never retried automatically (see below).

`403` if the caller isn't an admin (a dealer's own token works for every other route but this one). `404` for a referral that doesn't exist *or* belongs to another tenant — the same row is visible to any staff member via `GET /api/referrals`, so this can't be used to probe for IDs across tenants; only the write is admin-gated. A repeat call with the same target status returns `200` with the unchanged current state rather than erroring or re-logging.

**Refuses to touch a `closed` referral at all** (`409`) — that status has its own dedicated endpoints below precisely so `status` and `closed_at`/`reward_eligible_at` can never disagree; this endpoint won't risk moving a referral out of `closed` while leaving a stale hold behind it.

### `POST /api/referrals/:id/close`

Admin-only. Starts the 7-day reward hold: sets `status = 'closed'` and `closed_at = now()` in the same transaction, so the two can never disagree. `reward_eligible_at` (`closed_at` + 7 days) is derived automatically by a database trigger, not set here — see `supabase/README.md`'s billing-schema migration entry for why that's a trigger and not a `GENERATED` column.

Idempotent: closing an already-closed referral is a `200` no-op, not an error — no new `audit_log` row. Rejects (`409`) a `declined` or already-`rewarded` referral (closing either doesn't mean anything), and rejects (`409`) outright if the tenant's own `billing_status` isn't `active` — there's no point starting a hold toward a reward this tenant currently can't be charged for. Every actual transition writes an `audit_log` row (`action: 'referral.closed'`, `metadata: { from, to: 'closed' }`) naming who closed it and when.

```json
{ "id": "...", "status": "closed", "closed_at": "...", "reward_eligible_at": "..." }
```

### `POST /api/referrals/:id/reopen`

Admin-only. Undoes a close — but only while there's genuinely something to undo, both checked in the same guarded `UPDATE`'s `WHERE` clause (not just an earlier `SELECT`), since the reward-issuance worker runs on its own schedule, not this request's:

- `reward_issued_at` must still be `null` — once a card is out, reopening is **permanently rejected**, full stop.
- `now()` must still be before `reward_eligible_at` — once the 7-day hold has run out, the referral is eligible whether or not the worker has actually gotten to it yet, and reopening is rejected (`409`) even though nothing has been issued.

Reverts `status` to whatever it was immediately before closing — read back from that close action's own `audit_log` row (`metadata.from`), not a separately stored column, so there's exactly one place that fact lives. Clearing `closed_at` also clears `reward_eligible_at` automatically (the same trigger, run in reverse: `null + 7 days` is `null`). Writes its own `audit_log` row (`action: 'referral.reopened'`).

```json
{ "id": "...", "status": "new", "closed_at": null, "reward_eligible_at": null }
```

### `GET /api/links/:code`

Public — no auth, rate-limited (30/min per IP). Resolves either an invite or a share code for the customer page or the lead page to render its greeting. Returns the referrer's first name only — never phone/email — and an *effective* status (`active`/`used`/`expired`) that accounts for `expires_at` even though nothing proactively flips the stored column. An unknown code and an expired one both come back as a plain 404: nothing distinguishes "never existed" from "used up."

```json
{
  "kind": "share",
  "status": "active",
  "referrer_first_name": "Sarah",
  "tenant": { "name": "Acme", "reward_amount_cents": 5000, "reward_currency": "USD", "branding": {} }
}
```

### `POST /api/links/:code/share`

Public — no auth, rate-limited (10/min per IP). The customer taps "Get my referral code": idempotent per customer — the first call mints a share-kind link off of whatever link got them here (their invite, or — for a referred friend who's since become a customer — their own share link), so a referral chain can extend to any depth without special-casing link kinds; every call after that returns that same persistent link instead of minting another, so a customer has exactly one reusable code, forever.

```json
{ "code": "MvWNLtZkQh", "url": "/50/refer/MvWNLtZkQh", "status": "active", "created_at": "..." }
```

### `POST /api/links/:code/referrals`

Public — no auth, rate-limited (5/min per IP, the tightest of the three since this is the actual lead-capture write). `:code` must be a share-kind link — and, since share links are now persistent (see `POST /api/links/:code/share` above), the same code can be submitted against any number of times by different friends, each producing its own independent referral. Body: `{ "name", "email", "phone"?, "message"? }` — email is required (no SMS channel, matching the schema). A submission whose email or phone matches the link's own customer is rejected as a self-referral, returning `409` — distinct from the `404` for a code that never existed or isn't a share link.

```json
{ "id": "...", "submitted_at": "..." }
```

Also notifies — best-effort, invisible to this response either way — the dealer who actually owns this lead (see "How the dealer gets notified of a new lead" below).

### `PUT` / `GET` / `DELETE /api/tenant/tremendous-credentials`

Admin-only. Lets a company connect *its own* Tremendous account — API key, funding source, and campaign — so `PATCH /api/referrals/:id/status` pays rewards from that company's own card, under that company's own campaign, never a shared platform account. `PUT` body: `{ "api_key", "funding_source_id", "campaign_id" }` — all three required; `campaign_id` isn't optional because Tremendous's own API rejects an order that has neither a campaign nor a products list (confirmed against their real sandbox, not just assumed from docs).

`GET` and the `PUT` response only ever return `{ "configured": true|false, "funding_source_id", "campaign_id", "connected_at" }` — the key itself is write-only from here on out; nothing in this API ever decrypts it back to a client, not even the admin who set it. See "How a reward actually gets issued" below for how it's stored and used. `DELETE` clears all four columns (`{ "configured": false }`).

### `POST /api/billing/checkout-session`

Admin-only. Starts the tenant's one-time activation charge — Stage 2 of Stripe billing (see `supabase/README.md`'s billing-schema entry for Stage 1). Creates a real Stripe Checkout Session (`mode: 'payment'`) for `activation_fee_cents`, using `price_data` inline rather than a Stripe catalog price id, since pricing is per-tenant and variable. `payment_intent_data.setup_future_usage: 'off_session'` is what saves the payment method used here for Stage 4's later off-session per-referral charges. `payment_method_types` is whatever the tenant's own `payment_method_type` column says (`card` or `us_bank_account`) — never accepted as input, since the database itself already guarantees that value is consistent with the tenant's own pricing (see `tenants_card_requires_low_charge` in `supabase/README.md`).

Also computes and stores `monthly_spend_cap_cents` from the tenant's own `per_referral_charge_cents` (roughly 20 referrals' worth) rather than leaving it at the schema's flat default — a higher-reward tenant would otherwise hit that default cap after two or three referrals. Recomputed every call; harmless if called more than once before the customer completes checkout.

`409` if the tenant has already completed activation (`activation_paid_at` is already set) — this doesn't create a second charge. `success_url`/`cancel_url` are built from the *request's own* origin (`req.protocol`/`req.get('host')`, respecting `TRUST_PROXY` the same way the rate limiter does) — not `FRONTEND_BASE_URL` — since the two redirect pages below are served by this same app, not wherever the tenant-branded frontend pages happen to live.

```json
{ "url": "https://checkout.stripe.com/c/pay/cs_...", "session_id": "cs_..." }
```

**`GET /billing/activation-success.html` / `GET /billing/activation-cancelled.html`** — plain static pages (no framework, no JS), served by this same Express app via `express.static` (`server.js`, mounted at `/billing`; files in `api/public/billing/`). Success confirms activation is processing and notes that a bank-account payment takes a few business days; cancelled says nothing was charged and to ask an admin to restart activation. These are what Stripe Checkout actually redirects back to — they didn't exist when this endpoint was first built, which meant the redirect URLs pointed nowhere real; fixed alongside the rest of this section.

### `POST /api/webhooks/stripe`

No auth in the usual sense — authenticity comes from verifying the `Stripe-Signature` header against the raw request body (`src/lib/stripe.js`'s `verifyWebhookSignature`), not a bearer token. This is why `server.js` mounts this route *before* the app-wide `express.json()`: the signature covers the exact raw bytes Stripe sent, and this route applies its own `express.raw()` specifically so those bytes are still available when it runs. A missing or invalid signature is a `400`, logged server-side, before any event data is ever trusted.

**Idempotent against redelivery, uniformly**: every write this route makes that originates from a specific Stripe event goes through one insert into `billing_events` first — `INSERT ... ON CONFLICT (stripe_event_id) DO NOTHING RETURNING id` — before touching `tenants` at all. No row back means this exact event was already processed; the handler logs it and returns, doing nothing further. This is the same idempotency-via-unique-constraint pattern `gift_card_transactions.idempotency_key` already uses, applied to "has this webhook event been handled" instead of "has this reward been paid."

**Fails loudly, never silently, on a write that should have worked** (`src/db.js`'s `assertRowsAffected`, used throughout this route and `withServiceRole` generally): a guarded `UPDATE` that affects 0 rows is really only supposed to happen when the target is *already* in the state the write was trying to reach (a legitimate race between two events, or a redelivery) — every handler here re-checks for exactly that before treating 0 rows as fine. If it isn't that — the role can't actually write the row, or the row doesn't exist — `assertRowsAffected` throws, naming the table, the id, and `current_user`/`session_user` (queried at the moment of failure), and the request comes back `500` so Stripe retries rather than the failure vanishing into a `200`. This exists because it already happened once: an earlier version of `withServiceRole` was tested against the wrong local role, silently updated 0 rows, and returned success — see "How dealer auth works" above.

Five event types handled:

- **`checkout.session.completed`** — records `activation_checkout_completed_at` on the named tenant unconditionally (regardless of `payment_status`; this alone has no legitimate reason to affect 0 rows, so it asserts directly, no re-check needed) — this is what makes a stalled ACH activation queryable rather than invisible (see below). Then, only if `payment_status === 'paid'`, activates the tenant: stores `stripe_customer_id`/`stripe_payment_method_id` (the latter fetched via a follow-up `GET /v1/payment_intents/:id`, since the webhook payload only gives that id as a string) and sets `billing_status = 'active'`/`activation_paid_at`.
- **`checkout.session.async_payment_succeeded`** — the delayed-payment-method outcome: runs the exact same activation logic as the paid branch above. **This closes a real gap**: `checkout.session.completed` can fire with `payment_status: 'unpaid'` for `us_bank_account` (ACH) specifically, since Checkout completes as soon as the customer submits their bank details, days before the debit itself clears — this event is what actually says it cleared.
- **`checkout.session.async_payment_failed`** — the other half of that gap: the debit failed. Records a `billing_events` row (`event_type: 'payment_failed'`, the real reason from the PaymentIntent's `last_payment_error`) and leaves `billing_status` at `'pending'` — the tenant was never active, so there's nothing to suspend; a fresh `POST /api/billing/checkout-session` call is how they retry.
- **`payment_intent.payment_failed`** — reads `tenant_id` from the PaymentIntent's own `metadata` (set when it was created — see `createCheckoutSession`), sets `billing_status = 'suspended'`, and records the decline reason (`last_payment_error.message`) in `billing_events`. A PaymentIntent with no `tenant_id` metadata (not one of ours) is logged and ignored, not an error.
- **`charge.dispute.created`** — resolves `tenant_id` via a follow-up PaymentIntent lookup (the Dispute object itself doesn't carry it), suspends billing the same way, and logs loudly (`console.error`) regardless — real money at risk always gets a loud log, not just a quiet ledger row. A dispute whose tenant can't be resolved is logged for manual review rather than silently dropped.

Every other event type is acknowledged (`200`) without action — Stripe retries a non-2xx with backoff, which only makes sense for an event this handler actually intends to act on.

**A stalled ACH activation is queryable, not invisible**: a tenant with `billing_status = 'pending'`, `activation_paid_at` still null, and `activation_checkout_completed_at` set more than a few days ago has a bank debit that either failed silently (the `async_payment_failed` webhook never arrived — Stripe delivery isn't guaranteed to be instant or singular) or is taking unusually long. `supabase/README.md`'s `tenants_stalled_activation_idx` makes finding one cheap; how long is "too long" and what to do about it (a support workflow, an alert) is intentionally left to whatever queries it, not baked into the schema as a stored rule.

**Verified live against Stripe's real API, post-deploy, on Render**: signature verification against an actual Stripe-signed payload (not this project's own re-implementation of the HMAC signing scheme below), real event parsing, and handler validation across the event types above — all confirmed working end to end once this endpoint was reachable from outside this sandbox and registered with a real Stripe account. Every other scenario in this file's "Verified" section still describes local stand-in testing (`api.stripe.com` remains unreachable from *this* development sandbox, confirmed directly) — the real-API verification happened against the deployed service, not in this environment, and covers this route's own scope (signature verification, event parsing, the five handlers above), not Stage 4's `chargeOffSession` (off-session PaymentIntent creation/confirmation), which exercises a different Stripe capability and has not itself been run against the real API yet — see that section below.

## How the invite email works

`src/lib/postmark.js` is a thin wrapper over Postmark's HTTP API (no SDK dependency — just `fetch`, built into Node 22). `src/lib/inviteEmail.js` builds the subject/HTML/text from the tenant's name and reward amount, so the copy is never hardcoded to one tenant's numbers.

**Sender identity**: a tenant with its own verified domain (`tenants.send_domain_verified` + `send_from_address`/`send_from_name`, columns that have existed since the schema was first designed) sends as that domain. Every other tenant — today, that's all of them — falls back to the platform's single verified sender, `EMAIL_FROM_ADDRESS` (currently `ben@goodstewardstructures.com`, verified in Postmark). Nothing is hardcoded in application code; both are configuration, read at send time.

**The link in the email** is built by `buildInviteUrl()` in `routes/customers.js`: if `FRONTEND_BASE_URL` is set, it's `<FRONTEND_BASE_URL>/fifty-template-customer.html?code=...` — a real, working link wherever the static pages actually are — rather than the tenant's domain + the `/50/...` path scheme from earlier responses, which has no routing layer behind it and won't resolve. That fallback is still there for a deployment that hasn't set `FRONTEND_BASE_URL` yet, but it's not clickable until one exists. This is also the exact URL shown in the dealer page's confirmation box, so what a dealer sees matches what actually got emailed.

**Never blocks or reverts the core action**: the send is attempted only once the customer + link transaction has committed, and its failure is caught and reported, never thrown back as a request failure — a real customer and a real, usable link exist either way, whether or not Postmark cooperated.

## How the dealer gets notified of a new lead

`POST /api/links/:code/referrals` (a friend submitting the lead form) also emails **whichever dealer actually owns this lead** — the dealer who originally invited the customer that shared this link — not a fixed address, since that's the person who needs to follow up. `src/lib/leadNotificationEmail.js` builds the subject/body from the tenant's name, the dealer's name, the lead's own name/contact/message, and the referring customer's name.

**Who "owns" a lead, and where that comes from**: the caller here is `anon` — a friend filling out a lead form isn't logged in, and `anon` has no table access at all (see "How the public routes stay safe without an account" below). So the dealer's email/name, the referrer's name, and the tenant's sender config all come back as extra columns from `submit_referral()` itself (`supabase/migrations/20260906010000_submit_referral_dealer_notification.sql`) — the same narrow, security-definer function that already does the insert — rather than a second query the route has no privilege to run. A customer with no inviting dealer on record (auto-created from an earlier referral conversion, not entered by a dealer directly) comes back with a null `dealer_email`; the route treats that as "nothing to notify," not an error.

**Every admin on the tenant gets a copy too** — not hardcoded to any one person, and not conditional on the dealer path failing; it's a standing visibility thing. `submit_referral()` also returns `admin_emails` (`array_agg` over every `users` row with `role = 'admin'` on that tenant — null if there are none). The dealer (when there is one) gets the `To`; every admin gets `Cc`. When there's no dealer on record, the admin(s) become the `To` instead of being dropped — the lead still needs a human, and an admin is the fallback. Only truly skip sending when there's neither a dealer nor an admin to reach.

**Same sender-resolution and best-effort rules as the invite email above** — tenant's own verified domain if set, else the platform default; attempted only after the referral is safely committed; never blocks or reverts it. One difference: since the caller submitting the lead form is the anonymous friend, not the dealer, whether this notification succeeded is never reported back in the public response either way — there's no one on that end of the request who should see it. A failure is only visible in the server's own logs.

## How a reward actually gets issued manually (the pre-billing, per-tenant Tremendous flow)

Each tenant connects their own Tremendous account (`PUT /api/tenant/tremendous-credentials` above) — their own API key, funding their own card via their own funding source id, under their own campaign (their own branding and choice of reward — e.g. a campaign locked to Amazon.com gift cards). `PATCH /api/referrals/:id/status` is where that gets used: transitioning a referral to `rewarded` looks up *that referral's own tenant's* credentials and, only if all three (key, funding source, campaign) are on file, places one Tremendous order for the referrer (the customer who shared the link), for that tenant's own `reward_amount_cents`/`reward_currency`. There is no shared platform Tremendous account anywhere in this code — a tenant with nothing (or only partially) connected simply never has an order attempted, same as before this integration existed.

**Encrypted at rest, never returned**: `tenants.tremendous_api_key_encrypted` is ciphertext (`pgp_sym_encrypt`, pgcrypto), decrypted only inside the one query that needs the plaintext key to actually call Tremendous — held in memory just long enough to make that one HTTP call, never logged, never part of any API response. `TENANT_CREDENTIALS_ENCRYPTION_KEY` (the passphrase) lives only in this API's own environment, never in the database — losing it makes every tenant's stored key permanently undecryptable, same trade-off as losing any other password-hashing pepper.

**A reward is attempted at most once per referral, ever** — this is the part that actually matters, since it's real money: before calling Tremendous, the request claims an idempotency slot by inserting a `gift_card_transactions` row with `status = 'pending'` and a unique `idempotency_key` (`<referral_id>:referrer`), using `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING id`. Only a request that actually got a row back proceeds to call Tremendous; a concurrent or later request for the same referral sees the conflict, gets nothing back, and does not call Tremendous at all. This holds under genuine concurrency, not just sequential double-clicks — verified by firing 10 simultaneous `PATCH` requests at the same referral and confirming exactly one Tremendous call and one `gift_card_transactions` row resulted (see "Verified" below). The Tremendous call itself happens *after* that claim commits, outside any open database transaction (a slow external HTTP call should never hold one open); the outcome — `issued` with Tremendous's own order id, or `failed` with nothing further recorded — is written back to that same row in a second, separate transaction.

**A failed attempt is not retried automatically.** If Tremendous rejects the order (an underfunded funding source, a bad key), the `gift_card_transactions` row is left `status = 'failed'` and the referral stays `rewarded` regardless — the status change and the reward are two different guarantees, and a payment failure should never look like the referral itself is stuck. But because the idempotency slot is already claimed, clicking "mark as paid" again on that same referral will not try Tremendous a second time; today, recovering from a failed attempt means fixing the underlying problem (funding the card, rotating the key) and handling that one reward manually — see "Not yet built" below.

This is a genuinely different relationship from the automated worker below: here, the *tenant's own* Tremendous account funds and issues the reward. Stage 4's worker instead has the *platform* charge the tenant via Stripe and fund the reward itself — a tenant's Tremendous credentials (or lack of them) are irrelevant to that path.

## How the reward-issuance worker actually works (Stage 4)

`src/workers/rewardIssuance.js` — `runRewardIssuanceCycle()` — is not an HTTP endpoint. It's meant to run on a schedule via an external scheduler; `npm run reward-issuance` (or `node src/workers/runRewardIssuance.js` directly) is the CLI entry point that actually invokes it. `render.yaml` (repo root) defines a Render Cron Job that runs it hourly — see its own comments for the schedule trade-off and what still needs setting in the Render dashboard before that cron job's first real run.

No logged-in user exists for any of this, so every read and write goes through `withServiceRole`, same as the webhook handlers above.

**Candidates**: referrals where `closed_at` is set, `reward_eligible_at <= now()`, and `reward_issued_at` is still null, excluding any referral that already has a `billing_events` row (`event_type = 'referral_charge'`) in `'succeeded'` or `'needs_refund'` — both are terminal outcomes for that referral as far as this worker is concerned, ever. Per referral, in order:

1. **Claim it** — re-verify eligibility from scratch inside a `for update ... skip locked` transaction (a referral already locked by a concurrent invocation is silently skipped this cycle, not waited on or double-claimed), confirm the tenant's `billing_status` is `'active'` and it's missing neither `stripe_customer_id` nor `stripe_payment_method_id` (logged as a data-integrity error, not a normal skip, if it's `'active'` but missing either — that combination should be impossible), check the monthly spend cap (see below), then snapshot the tenant's current `per_referral_charge_cents`/`reward_amount_cents`/`platform_fee_cents` into a new `'pending'` `billing_events` row.
2. **Charge it off-session** — `chargeOffSession()` in `src/lib/stripe.js`: one call creates *and* confirms a PaymentIntent (`confirm: true`, `off_session: true`) against the tenant's saved payment method, with a required `Idempotency-Key` derived from the referral id alone (`referral_charge:<referral-id>`) — every attempt at this referral's charge, ever, from any process, uses the same key. A synchronous decline is a thrown error, same shape as every other Stripe call in this codebase; the `billing_events` row is marked `'failed'` (not retried by this same run, but not blocked from a future cycle's attempt either — see below) and `payment_intent.payment_failed` (already built in Stage 3, which anticipated `metadata.referral_id` for exactly this) is what actually suspends the tenant once Stripe delivers that webhook — this worker never duplicates that suspension itself.
3. **Issue both gift cards, only after the charge succeeds** — `per_referral_charge_cents` is `reward_amount_cents * 2 + platform_fee_cents` specifically because both sides of the referral get paid: the referrer, and the referred friend. The friend has no `customers` row of their own until this point — one is found-or-created via `customers.source_referral_id` (a true one-time claim, `INSERT ... ON CONFLICT (source_referral_id) DO NOTHING`, not a heuristic email match that could merge them into an unrelated customer a dealer happened to enter with the same address). Each leg is claimed via `gift_card_transactions.idempotency_key` (`<referral-id>:referrer` / `<referral-id>:new_customer` — no partial `WHERE`, a true one-time claim forever, same pattern the manual flow above already uses) before calling `src/lib/giftCardProvider.js`, outside any open transaction.
4. **Only once *both* legs are `'issued'`** does `referrals.reward_issued_at` get set (`status` → `'rewarded'`, same as the manual flow). If either leg fails — or *anything else* goes wrong after the charge succeeds, including a bug or a crash between the two legs (confirmed live: without this, a crash left a `'succeeded'` `billing_events` row with `reward_issued_at` still null and no way back into the candidate query, ever — silently stuck) — the `billing_events` row moves to `'needs_refund'` instead, naming which leg(s) failed and why, and is logged loudly (`console.error`). **The charge is never retried once a referral reaches `'needs_refund'`** — a human resolves it from there; any gift card that *did* go out on the other leg was real and can't be clawed back automatically.

**Three independent layers of idempotency**, deliberately, since this is the one place in the codebase that moves real money with nobody watching:

- Stripe's own `Idempotency-Key` (derived from the referral id) is authoritative against ever actually charging a card twice, even under a genuine race between two overlapping worker runs — Stripe returns the identical PaymentIntent to both.
- `billing_events_one_referral_charge_idx` (Stage 1's partial unique index) is the database-level backstop: at most one `referral_charge` row per referral can ever reach `'succeeded'`/`'needs_refund'`. It deliberately does *not* cover `'pending'` — so two processes can, in a genuine race, both get as far as inserting their own `'pending'` claim row and both call Stripe (with the same idempotency key, so only one charge actually happens) — the loser's own follow-up `UPDATE ... SET status = 'succeeded'` then hits the unique-index conflict and is caught explicitly: marked `'failed'` (not left dangling as `'pending'` forever) rather than proceeding to issue a reward twice.
- `gift_card_transactions.idempotency_key` (no partial `WHERE` — unique across every row, forever) makes each leg's claim a true one-time claim.

**Monthly spend cap**: calendar-month, UTC, based on `'succeeded'` `referral_charge` `billing_events` rows only (a failed or needs-refund charge doesn't count against it) — a deliberate simplification, not a hidden assumption; a rolling 30-day window or a tenant-timezone-aware boundary would both be defensible alternatives.

**Operational safety rails**, added before this worker ran unattended on a cron schedule — this is real money moving with nobody watching:

- **`--dry-run`** (`node src/workers/runRewardIssuance.js --dry-run`, or `npm run reward-issuance:dry-run`): previews the whole cycle — read-only, no Stripe calls, no gift card provider calls, no database writes at all, not even a `'pending'` claim row — logging one `would_charge`/`would_skip` line per candidate plus a `dry_run_summary` line with the total intended spend. The intended use: run this before trusting a cron job to run the same cycle for real, especially the first time against a live Stripe account.
- **`REWARD_CYCLE_MAX_CENTS`**: a global ceiling on one cycle's *total* intended charges, independent of any tenant's own `monthly_spend_cap_cents` — a per-tenant cap can't catch a bug that makes every tenant eligible at once (a bad migration, a bulk `reward_eligible_at` backfill). Computed the same way `--dry-run` computes its preview, *before* any real work happens; exceeding it aborts the entire cycle — nothing is charged, not even the referrals that would have fit under it — logs loudly, and exits non-zero. **Required** for a real (non-`--dry-run`) invocation: the worker refuses to start rather than silently picking a default ceiling for you. Not required for `--dry-run`, which never spends anything regardless.
- **A Postgres advisory lock** (`pg_try_advisory_lock`, a fixed key dedicated to this worker) makes an entire cycle single-flight: a second invocation that finds the lock already held logs `lock_not_acquired` and exits immediately (`0` — this is an expected, benign outcome under an overlapping cron run, not a failure) without touching the database further. This is the actual guard against two overlapping runs both claiming the same referral; `claimReferralCharge`'s own `for update ... skip locked` (see above) is real but only a partial defense on its own — see that section's comment for why. Confirmed live: two genuinely concurrent invocations against the same candidate set — one processed everything, the other logged `lock_not_acquired` and exited clean, touching nothing.
- **Structured, one-line-per-referral logs**: every finalized outcome (`issued`, `needs_refund`, `charge_failed`, `skipped`, or a dry-run `would_charge`/`would_skip`) is one `console.log` line prefixed `REWARD_WORKER referral_outcome`, a JSON object naming the referral id, tenant id, intended amount, outcome, and (when relevant) why — grep-able from Render's log tab without attaching a debugger. Cycle-level outcomes (`cycle_complete`, `cycle_aborted`, `lock_not_acquired`, `dry_run_summary`) are logged the same way, each prefixed `REWARD_WORKER`.

**The gift card provider is still unresolved as a business matter** (Tremendous declined to support this platform-funded model; Tango and Amazon Incentives are both pending an LLC and EIN). `src/lib/giftCardProvider.js` is a one-function interface (`issueGiftCard(...)` resolves to `{ providerTransactionId, raw }` or throws) so the worker never depends on a specific provider's client — only `src/lib/giftCardProviders/stub.js` exists today, selected via `GIFT_CARD_PROVIDER` (defaults to `'stub'`). Dropping in a real provider later means adding one file under `giftCardProviders/` with the same shape and flipping that env var; the worker itself never changes. `GIFT_CARD_STUB_FAIL_KEYS` (comma-separated `idempotency_key` values) makes the stub fail on demand, for exercising the `needs_refund` path — test-only, never set outside a local/test environment.

**A misconfigured `DATABASE_URL` role fails loudly here too, but not only via `assertRowsAffected`**: that helper only catches a *write* silently affecting 0 rows, because the caller already knows which row it targeted. This worker's very first step is a broad *read* (the candidate query) with no such anchor — confirmed live, pointed at a non-superuser role, the candidate query is silently RLS-filtered to zero rows and the worker completes a clean-looking `"0 candidates, 0 errors"` cycle, forever, with no reward ever issued and nothing to alert on. `db.js`'s new `assertServiceRoleConnection(client)` closes this: called once at the very start of the cycle, it queries `current_setting('is_superuser')` directly and throws immediately, naming `current_user`/`session_user`, if the connection isn't actually a superuser — turning a silent, permanently-broken worker into an immediate, loud deployment error.

## How the public routes stay safe without an account

There's no JWT here — a friend filling out a lead form isn't logged in — so these three routes can't lean on RLS the way the dealer routes do. Instead they're the *only* thing Postgres lets the `anon` role touch at all: three narrow, `security definer` functions (`resolve_link`, `create_share_link`, `submit_referral` — `supabase/migrations/20260826030000_public_link_functions.sql`), each doing one specific, vetted thing and returning only the columns it should. `anon` has no grants on any table directly, so a code path that accidentally queried a table instead of calling one of these functions would simply fail with a permission error, not silently succeed. Each request still runs as `anon` (`withPublicTransaction` in `src/db.js`), matching the same impersonation pattern as the dealer routes rather than connecting with some broader "service" role.

Everything else is what actually carries the weight for an endpoint anyone on the internet can hit: strict `zod` validation (including a regex on `:code` itself, rejected before it ever reaches the database), per-route rate limiting tuned to how often a real visitor would legitimately call each one (`src/middleware/rateLimit.js`), and error responses written to never leak more than a real visitor needs — "not found" and "expired" are indistinguishable, and a `POST` that hits a genuine double-submit race gets caught by the database's own unique constraint on `referrals.referral_link_id`, not just an application-level check that a concurrent request could slip past.

## How dealer auth works — and why it isn't bypassing RLS

Every route requires `Authorization: Bearer <token>`, verified in `src/middleware/auth.js`. That only establishes *identity* (the caller's `auth.uid()`) — it does not look up or trust a tenant or role from the token.

**Verified against Supabase's JWKS, not a static secret**: this project's Supabase tokens are signed with an asymmetric key (ES256) that Supabase rotates on its own, not the legacy shared HS256 secret — so `requireAuth` fetches the project's current public signing key from `<SUPABASE_URL>/auth/v1/.well-known/jwks.json` (via `jwks-rsa`, cached in memory for 10 minutes) and verifies against whichever key matches the token's `kid`, restricted to `ES256` specifically — never left open to whatever algorithm a token happens to claim, which is the classic "alg confusion" hole in JWT verification. `SUPABASE_URL` is the only required config for this; `SUPABASE_JWKS_URL` exists solely to point it at a local stand-in for tests (see "Verified" below).

**Where the token comes from**: real Supabase Auth, not a pasted string. The dealer page signs in against `<SUPABASE_URL>/auth/v1/token?grant_type=password` directly (no `supabase-js` — it's a plain page, so this is one `fetch` with the project's public anon key), gets back an access + refresh token pair, and stores them in `localStorage`. Every `apiFetch` call attaches the access token; a `401` triggers exactly one refresh-token attempt (`grant_type=refresh_token`) before giving up and signing the page out — no silent retry loop, no token ever sent after a refresh fails. [`../supabase/README.md`](../supabase/README.md)'s "Staff accounts" section covers how a person actually gets an account in the first place (there's no self-serve signup).

Each request then runs inside a Postgres transaction that impersonates that identity (`src/db.js`, `withUserTransaction`):

```sql
SET LOCAL ROLE authenticated;
SELECT set_config('request.jwt.claim.sub', '<verified user id>', true);
```

This is exactly the session state Supabase's own PostgREST layer sets up, so `auth.uid()` and the RLS policies from `supabase/migrations/20260826020000_rls_policies.sql` apply unmodified. The API has no separate "is this the caller's tenant?" logic of its own — a dealer only ever sees or writes their own tenant's rows because Postgres, not this code, rejects anything else. This holds for the search filter too: even a `query` string engineered to match another tenant's data returns nothing, because the join it runs against (`referrals` → `referral_links` → `customers`) is RLS-scoped before the `WHERE` clause ever sees a row.

**Correction, confirmed live while building Stage 2 of Stripe billing:** the line that used to stand here claimed a role that bypasses RLS "would defeat the point" of the `SET LOCAL ROLE authenticated` pattern above. That had it backwards. `DATABASE_URL`'s own connection (`postgres`, per `.env.example` — the same superuser [`../supabase/README.md`](../supabase/README.md)'s "Staff accounts" section already relies on to bypass RLS for provisioning) *is* a role that bypasses RLS by default — that's exactly why `withUserTransaction` does `SET LOCAL ROLE authenticated` at all: it's a deliberate, scoped-to-one-transaction *downgrade*, giving up the connection's own bypass privilege so RLS applies as if the caller had only the access a real dealer/admin login would. `withPublicTransaction` downgrades to `anon` the same way. `withServiceRole` (`src/db.js`) is the third case: code with no logged-in user to downgrade *to* in the first place — a Stripe webhook (verified by signature, not a JWT) or the reward-issuance worker — which simply doesn't downgrade at all, using the connection's native privilege directly. See `POST /api/webhooks/stripe` below for where this is actually exercised, and "How the reward-issuance worker actually works" for `assertServiceRoleConnection` — a second safeguard, added for Stage 4, that catches the same class of misconfigured-role problem on the *read* side, where `assertRowsAffected` alone can't reach.

- **A real design correction, caught live rather than assumed**: `withServiceRole` (`src/db.js`) was first tested against the wrong role (a member of `authenticated`, not the actual superuser `DATABASE_URL` connects as in every real deployment) and silently updated 0 rows — RLS-filtered, no error. Re-tested against the actual superuser connection, every write above succeeded correctly. See "How dealer auth works" above for the corrected explanation this surfaced.
- **`assertRowsAffected`**: re-ran the exact scenario that surfaced the bug above — the same query, against the same wrong role — and confirmed it now throws immediately, naming the table, the id, and both `current_user`/`session_user` (both `"apiuser"`, correctly identifying the actual problem), instead of returning a silent success.
- **The ACH async gap, closed**: `checkout.session.completed` with `payment_status: 'unpaid'` sets `activation_checkout_completed_at` but leaves `billing_status` at `'pending'` — confirmed live. Backdating that timestamp 8 days and querying exactly what `tenants_stalled_activation_idx` is meant to serve correctly finds the stalled tenant. `checkout.session.async_payment_succeeded` for the same session then activates it correctly (`billing_status: 'active'`, `stripe_customer_id` set) and — a real gap in Stage 2 caught and fixed along the way — now also writes the `activation_charge` `billing_events` row that Stage 2 never actually wrote despite Stage 1's own schema comment saying it should. Redelivering that same event a second time changes nothing (still exactly one `billing_events` row). `checkout.session.async_payment_failed` on a second tenant: `billing_events` records the real decline reason (fetched from the PaymentIntent's `last_payment_error`), and `billing_status` correctly stays `'pending'` rather than being suspended — the tenant was never active in the first place.
- **The redirect pages**: `GET /billing/activation-success.html` and `.../activation-cancelled.html` both return `200` with the correct `<title>`, served by the running API server itself. `POST /api/billing/checkout-session`, called with a `Host` header set to a value distinct from any configured env var, produces `success_url`/`cancel_url` matching that exact host — confirming they're built from the request, not a hardcoded or misconfigured `FRONTEND_BASE_URL`.
- **Stage 3**: `payment_intent.payment_failed` with the tenant's own `tenant_id` in the PaymentIntent's `metadata` → `billing_status` flips to `'suspended'` and `billing_events` records the real `last_payment_error.message`; the identical event redelivered → no second row, no error; a PaymentIntent with no `tenant_id` metadata → logged and ignored, not treated as an error or a crash. `charge.dispute.created`, tenant resolved via a follow-up PaymentIntent lookup (the Dispute object itself doesn't carry `metadata`) → suspends the same way, records the dispute reason, and logs loudly (confirmed in the server's own output, not just the ledger); redelivered → no-op; a dispute with no resolvable PaymentIntent → logged for manual review rather than thrown or silently dropped. `POST /api/referrals/:id/close`, re-run against a now-suspended tenant → still correctly `409`s (this guard was built in Stage 2, re-confirmed here since Stage 3 is the first time a tenant actually reaches `suspended` through a real code path rather than a manual `UPDATE`).
- **Stage 3, verified live against Stripe's real API post-deploy**: once this endpoint was reachable and registered with a real Stripe test-mode account on Render, signature verification, event parsing, and handler behavior were all confirmed against genuine Stripe webhook deliveries — not this project's own re-implementation of the signing scheme, and not the local stub. This is the first part of Stripe billing verified against the real API rather than only local stand-ins.
- **Stage 4, against a local stripe/gift-card stand-in** (real Stripe verification of `chargeOffSession` specifically is still open — see its section above): five tenants seeded to cover the real branches. An eligible referral on an `'active'` tenant with a saved payment method → charged (real `Idempotency-Key` header sent, matching `referral_charge:<referral-id>`), both `gift_card_transactions` legs (`referrer`/`new_customer`) issued, a `customers` row auto-created for the friend via `source_referral_id`, `referrals.status` → `'rewarded'`, `reward_issued_at` set, pricing correctly snapshotted onto `billing_events` (`amount_cents: 19900`, `reward_amount_cents: 5000`, `platform_fee_cents: 9900`) — re-running the cycle afterward no longer selects this referral at all. A declined charge (stub forced) → `billing_events` `'failed'` with the real decline message, referral stays `'closed'`, **and remains eligible for a future cycle's retry** (confirmed: `'failed'` is not in the candidate query's exclusion list, unlike `'succeeded'`/`'needs_refund'`). A charge that succeeds but one gift card leg fails (`GIFT_CARD_STUB_FAIL_KEYS`) → `billing_events` → `'needs_refund'` naming the failed leg, the *other* leg's card genuinely `'issued'` and left that way (never clawed back), `reward_issued_at` stays null, and the referral is permanently excluded from future cycles. A `'suspended'` tenant's referral → skipped, no `billing_events` row created at all. A tenant whose spend cap would be exceeded by this referral's charge → skipped the same way, with the cap check based on the current calendar month's `'succeeded'` `referral_charge` total. **Two bugs caught and fixed live during this verification**, both described in more detail in their own code comments: (1) `customers_source_referral_id_idx` was originally a partial index (`WHERE source_referral_id IS NOT NULL`), which `ON CONFLICT (source_referral_id)` cannot infer against — Postgres requires an arbiter index whose predicate the `ON CONFLICT` clause matches exactly; fixed by making it a plain unique index, which needs no predicate since NULL is never equal to NULL for uniqueness purposes anyway. (2) An unrelated crash between the two gift-card legs (triggered by bug #1, but not specific to it) left a `billing_events` row stuck at `'succeeded'` forever, with no reward issued and no way back into the candidate query — fixed by wrapping both legs in a try/catch that routes *any* failure at that point to `'needs_refund'`, not just a provider-reported one. **A third, more serious class of silent failure was also caught and fixed**: pointing the worker at a non-superuser role didn't produce an error at all — the candidate query was silently RLS-filtered to zero rows, and the worker reported a clean `"0 candidates"` cycle, forever. `assertRowsAffected` doesn't catch this (it's a *read*, not a targeted write) — fixed by adding `assertServiceRoleConnection`, called once at the start of the cycle, which now throws immediately and by name (`current_user`/`session_user`) under the same misconfigured-role scenario, confirmed live; re-run against the real superuser role immediately afterward, the same cycle completes cleanly.
- **The operational safety rails**: `--dry-run` against a batch of real eligible referrals → one `would_charge`/`would_skip` line per candidate plus a correct `dry_run_summary` total, with zero new `billing_events` rows afterward and zero new requests reaching the Stripe stand-in (checked directly against its request log) — confirming it's genuinely read-only, not just "doesn't call Stripe." A real (non-dry-run) invocation with `REWARD_CYCLE_MAX_CENTS` unset → refuses immediately with a clear error, before any database access at all; `--dry-run` with it unset still works. `REWARD_CYCLE_MAX_CENTS` set below the batch's actual total intended spend → the cycle aborts, logs `cycle_aborted` with the real numbers, and — confirmed directly — creates zero `billing_events` rows for *any* candidate in the batch, not just the ones that would have pushed it over; exits non-zero. **The advisory lock, under genuine two-process concurrency**: launched two `runRewardIssuance.js` invocations at the same moment against the same eligible-referral set — one ran the full cycle to completion (5 issued, 1 retried a prior decline, 2 correctly skipped), the other logged `lock_not_acquired` and exited `0` within milliseconds, having queried nothing beyond acquiring (and failing to acquire) the lock itself. Structured logging: every outcome in every scenario above produced its own `REWARD_WORKER referral_outcome` line with the correct referral id, tenant id, amount, and outcome.

## The frontend prototype pages

The three static pages at the repo root (`fifty-template-dealer.html`, `fifty-template-customer.html`, `fifty-template-lead.html`) call this API directly — no build step, no framework, just `fetch()`. Each has an `API_BASE` constant near the top of its `<script>` block (next to the existing `TENANT` config object) — that's the one line to change per deployment.

- **Dealer page**: real login now — email + password against Supabase Auth directly (see "How dealer auth works" above), not a pasted token. Signed out, it shows a login form and nothing else; signed in, it shows "Signed in as ... · role", the send-referral form, and the referrals list, scoped to whatever `GET /api/referrals` returns for that person. The "mark as paid" toggle calls `PATCH /api/referrals/:id/status` for real; it's rendered disabled for a dealer (with a tooltip explaining why) since the endpoint is admin-only anyway — display-only, the server-side check is what actually matters. Its confirm dialog no longer claims this "sends the $50 gift card" (the original mockup's copy) — that would be false until the gift-card integration exists — and says so plainly instead. Any `401` from the API (including a failed token refresh) signs the page out rather than showing a confusing error. Submitting the "send referral" form shows "Emailed to ..." when it actually sent, or a plain explanation plus the link to send manually when it didn't — the copy-link box never disappears, it's just no longer the primary instruction.
- **Customer & lead pages**: their existing demo panels already worked as a manual code-entry fallback (lead page) or got simplified into one (customer page, which previously faked a referrer identity with free-text fields — now that identity always comes from a real backend row, there's nothing to fake).
- Since the friend-facing forms now hit a real backend that requires a real email, each page's original single "phone number or email" field became two fields — email (required) and phone (optional) — the one visible UI change beyond wiring, and a direct consequence of the schema decision to be email-only (no SMS).
- The dealer's referral list now shows one row per friend submission rather than per invited customer (see `GET /api/referrals` above) — same row/pill styling, different underlying data, which changes what's shown in each row (the friend's name/contact, plus who referred them) though not the page's look.
- The customer page's own onward **share** link is still built client-side, as `${window.location.origin}/fifty-template-lead.html?ref=...` — that hasn't changed. The dealer's **invite** link is now built server-side (see "How the invite email works" above) since it has to be a real, working URL before it's put in an email the API sends on its own, not just displayed for a human to copy.
- `routes/customers.js` and `routes/referrals.js` now also mount `cors()`, matching `routes/public.js` — safe here for the same reason it was safe there: auth is a bearer token the calling page must already possess and attach itself, never a cookie the browser sends automatically, so an open CORS policy doesn't add a CSRF-style risk. Without it, a static page served from any origin other than the API's own couldn't call these routes at all.

**Verified**: ran the full three-page flow through an actual headless browser (Playwright) against a live API + Postgres, with the pages served from a different origin/port than the API (genuinely exercising CORS, not masked by same-origin) — dealer submits the form → real confirmation with a working invite link → customer page resolves it and shares → lead page resolves the share link and submits → dealer's list picks up the new referral with the correct referrer attribution and searches for it correctly → an invalid code shows "not valid". Also checked: no-token and invalid-token states on the dealer page, and that empty-email submission is blocked client-side before ever reaching the API. The "mark as paid" toggle, separately, through the same kind of live browser run: an admin clicking it on a pending referral shows the (now provider-agnostic) confirm copy, calls the real endpoint, and the row flips to a disabled, checked "Marked paid" pill; a dealer's token gets the `403` alert and the toggle visibly reverts to unchecked rather than silently failing. ## Not yet built

The order-system webhook that would set `ordered` automatically instead of by hand, and per-tenant verified sending domains (every tenant currently sends invite emails through the one platform-wide verified address — separate from, and unrelated to, each tenant's own Tremendous credentials).

**Stripe billing** (see `supabase/README.md`'s billing-schema migration entry) is now all four planned stages: the one-time activation checkout, the full webhook handling (activation — both immediate and delayed-ACH-clearing — plus failed-payment and dispute suspension), close/reopen, and the reward-issuance worker itself (Stage 4 — see "How the reward-issuance worker actually works" above). One gap not deferred to a later stage but genuinely open: `tenants_select_own`'s RLS policy grants a tenant's *entire* row — including the billing/pricing columns (`platform_fee_cents`, `monthly_spend_cap_cents`, etc.) — to any staff member, dealer or admin alike, since Postgres RLS can't restrict individual columns within one policy. Mitigated at the API layer for now (every route builds its response from named fields, never `select *` or a spread of a raw `tenants` row or `getCallerContext`'s own ctx object — see its own comment in `src/db.js`), with `stripe_customer_id`/`stripe_payment_method_id` specifically never appearing in any response body; a security-barrier view or column-level grants would close this at the database level too, deliberately deferred as not worth the complexity yet.

**The worker's cron job is defined (`render.yaml`, repo root) but not yet actually running anywhere** — applying that Blueprint in the Render dashboard is what turns it into a real, live cron job; nothing has been deployed from it yet, and it's unverified against Render's real sync process for the reasons "Deploying (Render)" above explains. The schedule it defines (hourly) is a starting point, not a settled decision — see that file's own comment on the trade-off. `REWARD_CYCLE_MAX_CENTS` also has no value yet; the worker refuses to run for real until one is set in the dashboard.

**No real gift card provider exists yet** — see "How the reward-issuance worker actually works" above for the current state (Tremendous declined, Tango/Amazon Incentives pending business paperwork) and the provider-interface/stub design built around that gap. Every reward Stage 4 has ever issued, anywhere, is from the stub — no real gift card has gone out through this path.

**Stripe billing's real-API verification is split by stage**: the webhook endpoint (Stages 2-3's event handling) has been verified live against a real Stripe test-mode account, post-deploy (see its own "Verified live" note above) — signature verification, event parsing, and all five handlers. Stage 4's `chargeOffSession` (creating and confirming an off-session PaymentIntent) has **not** — it exercises a different Stripe capability than anything a webhook delivery touches, and everything about it in this file (including the `Idempotency-Key` behavior) is verified only against this project's own local stub, never a real charge. The onboarding Checkout Session flow (Stage 2) is likewise still stub-only. First real verification of either happens against a live Stripe test-mode account, same as the webhook endpoint was.

On the Tremendous integration specifically (the older, per-tenant manual flow — see "How a reward actually gets issued manually" above, distinct from Stage 4's platform-funded worker): a failed reward attempt is never retried automatically — recovering one today means fixing the underlying problem and handling that single reward by hand, not resubmitting through this API.
